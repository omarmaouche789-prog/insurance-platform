# Deployment: Render (API) + Vercel (web) + Railway (Postgres)

```
Browser ──> Vercel (apps/web, Next.js) ──/api/* rewrite──> Render (apps/api, Express) ──> Railway Postgres
                                                                  ├─> AWS S3 (documents)
                                                                  ├─> SendGrid (email)
                                                                  ├─> SmartyStreets (ZIP lookup)
                                                                  └─> Carrier APIs
```

The browser only ever talks to the Vercel domain. Vercel proxies `/api/*` to Render, so the refresh-token cookie stays first-party and no CORS setup is needed.

## 1. API on Render

1. **New → Blueprint** and point it at this repo. [`render.yaml`](render.yaml) defines the service: build, pre-deploy migrations, start command and health check.
2. Fill in the env vars marked `sync: false` (reference below).
3. Deploy. `prisma migrate deploy` runs before each new version goes live. Seed data is **not** loaded in production. To load it into a staging database, run `npm run -w apps/api prisma:seed` once from a shell.

With `NODE_ENV=production` the API **refuses to start** if any integration is unconfigured, and lists exactly what's missing. That's deliberate: silently falling back to local disk would lose uploaded documents on the next deploy. For a staging environment without real credentials, set `ALLOW_MOCK_INTEGRATIONS=true`.

## 2. Web on Vercel

1. **New Project** from this repo, with **Root Directory** `apps/web`. [`apps/web/vercel.json`](apps/web/vercel.json) installs from the monorepo root and builds `packages/shared` first.
2. Set `API_BASE_URL` to the Render URL, e.g. `https://insurance-marketplace-api.onrender.com`. Production builds fail if it's missing.
3. Back in Render, set `WEB_ORIGIN` and `APP_URL` to the Vercel URL.

## Environment variables

### API (Render)

| Variable | Required | Notes |
| --- | --- | --- |
| `NODE_ENV` | yes | `production` (set by `render.yaml`). |
| `DATABASE_URL` | yes | Railway's **public** connection URL (`*.proxy.rlwy.net`); `*.railway.internal` isn't reachable from Render. |
| `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` | yes | Generated by Render. Rotating them logs everyone out. |
| `FIELD_ENCRYPTION_KEY` | yes | 32 random bytes, base64: `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`. Encrypts SSNs and health info. **Losing or changing it makes existing applications unreadable.** Use a different key per environment and keep it in a secrets manager. |
| `WEB_ORIGIN` | yes | The Vercel URL (CORS). |
| `APP_URL` | yes | The Vercel URL, for links in emails. |
| `TRUST_PROXY` | recommended | `1` (Render's load balancer), so audit-log IPs are the client's. |
| `ACCESS_TOKEN_TTL`, `REFRESH_TOKEN_TTL` | no | Default `15m` / `30d`. |
| `AWS_S3_BUCKET` | yes* | Document storage bucket. |
| `AWS_REGION` | yes* | The bucket's region. |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | yes* | IAM user limited to the policy below. |
| `AWS_S3_KMS_KEY_ID` | no | Use a customer-managed KMS key instead of SSE-S3. |
| `AWS_S3_PREFIX` | no | e.g. `staging/`, to share a bucket between environments. |
| `SENDGRID_API_KEY` | yes* | Scope the key to **Mail Send** only. |

## Security notes for this release

- **Migration `20261002210017_tier1_security_admin_cms`** adds 2FA backup codes, login history, password-reset tokens, notifications, follow-ups, internal notes, blog posts, and new columns on `users`, `agent_profiles`, `document_requests`, `two_factor_secrets` and `commissions`. It backfills `users.twoFactorEnabled` and `document_requests.status` from existing data and runs automatically via `prisma migrate deploy`. It is additive: no columns are dropped.
- **TOTP secrets are now encrypted** with `FIELD_ENCRYPTION_KEY`. Secrets created before this release are plaintext; each one is re-encrypted the next time its owner signs in with an authenticator code. No manual step is needed.
- **Backup codes** are stored as HMACs keyed from `FIELD_ENCRYPTION_KEY`. Rotating that key invalidates every user's backup codes (their authenticator apps keep working).
- **Rate limiting** on login, 2FA, password reset and destructive admin actions is per API instance, in memory. Per-account lockouts are stored in Postgres and hold across instances. The limit is *Max login attempts* in System settings: 5 failed passwords or 5 failed 2FA codes in 15 minutes by default. Before System settings existed, the password limit was 10. Set `TRUST_PROXY=1` on Render or all clients share one IP-based bucket.
- **Migration `20261006225136_system_settings`** adds the `system_settings` table. It starts empty, and missing rows mean the defaults apply. Two defaults change behavior on deploy: sessions now end after **30 minutes without a refresh** (idle timeout), and accounts lock after **5** failed passwords instead of 10. Change either in `/admin/settings`.
- **Maintenance mode** is stored in Postgres, so it applies on every API instance (each one re-reads settings at most every 10 seconds). If the settings can't be read, the API uses the last values it read, or the defaults, rather than failing requests.
- **Suspension and deletion** revoke refresh tokens immediately; an access token that was already issued stays valid until it expires (`ACCESS_TOKEN_TTL`, 15 minutes by default).
- Blog featured images are stored with the same adapter as documents (S3 in production), under the `cms/` prefix, and served publicly through `/api/blog/images/:postId`.

## Integration setup

### S3

- Turn on **Block all public access** and **default encryption**. The app also sets SSE on every upload.
- Add a bucket policy that denies non-TLS requests (`aws:SecureTransport = false`).
- The IAM policy for the app's key should cover only the bucket (or prefix):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::YOUR_BUCKET/*"
    }
  ]
}
```

With a KMS key, the policy also needs `kms:GenerateDataKey` and `kms:Decrypt` on that key.

### SendGrid

Verify the `EMAIL_FROM` sender or domain (domain authentication gives better deliverability). Click and open tracking are turned off per message, so portal links aren't rewritten. Emails never contain PHI (plans, health info, rejection reasons or document contents), only a sign-in link. If a send fails, it's retried on 429/5xx and then logged. The action that triggered it still succeeds.

### SmartyStreets

Use a **secret** key pair (not an embedded/website key). Lookups are cached in memory for 24 hours. If Smarty is down or rejects the credentials, lookups fall back to the built-in state table and a warning is logged, so agent assignment keeps working.

### Carrier APIs

Each carrier code in the database (`BLUEPEAK`, `MERIDIAN`, `SUMMIT`, `HARBOR` in the seed) gets a URL/key pair. `HttpCarrierAdapter` speaks this generic contract. A real carrier's API (or EDI 834 feed) needs its own mapping behind the same `CarrierSubmissionAdapter` interface.

```
POST {CARRIER_X_API_URL}/enrollments
Authorization: Bearer {CARRIER_X_API_KEY}
Idempotency-Key: {applicationId}-{attempt}
{ "externalId", "attempt", "planId", "applicant": {...}, "healthInfo", "documentTypes" }
→ 2xx { "status": "accepted" | "rejected", "reference"?, "message"? }

POST {CARRIER_X_API_URL}/enrollments/{reference}/decision
Idempotency-Key: {applicationId}-decision
{ "externalId", "decision": "approved" }
```

- **Within one request:** timeouts, network errors, 408/425/429 and 5xx are retried up to 3 times with exponential backoff and jitter (honoring `Retry-After`). All tries send the same `Idempotency-Key`.
- **Across requests:** if every try fails, the application is marked `FAILED`. The applicant or agent can retry it. That retry is a new attempt with a new key, and the carrier should also dedupe on `externalId`.
- **Other 4xx:** these aren't retried. The response body is never logged, because carriers may echo the PHI-bearing payload back.
- **Audit:** every response or failure is written to the audit log as `carrier.response`, with the outcome, reference, HTTP status, number of tries and duration. The payload is never included.

## Before going live

- **Upload size through Vercel:** documents can be up to 5 MB, and uploads pass through the Vercel rewrite. Check Vercel's current request-body limit for external rewrites on your plan. If it's lower, reduce `MAX_DOCUMENT_BYTES` in `packages/shared/src/applications.ts` or upload directly to the Render URL.
- **Failed carrier approval notices** are logged (`carrier.response` with `outcome: ERROR`) but not retried automatically. They need a manual follow-up, or a background job.
- **Existing local-disk documents:** any stored under `STORAGE_DIR` before switching to S3 aren't migrated. There are none in the shared Railway database right now.
- **Real carrier mappings:** the generic contract above stands in until each carrier's actual API spec is implemented.
